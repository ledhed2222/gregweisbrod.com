# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # vite dev server on port 3000 (alias: npm start)
npm run typecheck  # tsc -p tsconfig.json && tsc -p tsconfig.node.json
npm run lint       # eslint .
npm run test       # playwright test (integration; builds + previews first)
npm run build      # npm run typecheck && vite build -> build/
npm run preview    # serve the production build
```

`typecheck` runs both tsconfigs deliberately. The app config covers `src` and `tests`; the node one covers `vite.config.ts` and `playwright.config.ts`, which would otherwise never be typechecked. Both set `noEmit`, so neither writes output — don't switch this to `tsc -b`, which forces `composite` and litters the repo root with `vite.config.js` and `.tsbuildinfo` files.

**Tests.** `tests/smoke.spec.ts` is the whole suite: it loads every route directly, clicks through the nav, checks the 404 path, and asserts that no route produces a `console.error` or an uncaught exception. It imports `PAGES` from `src/pageDefs.ts`, so adding a page automatically adds coverage — keep it that way rather than hardcoding paths.

Playwright's `webServer` runs `npm run build && npm run preview`, so tests hit the **production build**, not the dev server. That means a failure can come from the build as easily as from the app. Locally it reuses an already-running server; in CI it doesn't. Run a single test with `npx playwright test -g "About"`, and debug with `npx playwright test --headed` or `npx playwright show-trace test-results/<dir>/trace.zip`.

Note that `getByRole('heading')` matches nothing on this site — the `Header` component renders `<header>`, not an `<h1>`–`<h6>`. Locate that text directly.

CI (Node 22) runs lint + typecheck in `.github/workflows/lint.yml` and the integration tests in `.github/workflows/test.yml`; both run on every pull request.

`.husky/pre-commit` runs `lint-staged`: `eslint --fix` on staged JS/TS (which formats too, via `eslint-plugin-prettier`) and `prettier --write` on staged `scss,css,json,md,html`.

## Deployment

Merging to `master` triggers `.github/workflows/firebase-hosting-merge.yml`, which builds and deploys to Firebase Hosting (project `gregweisbrodsite`). Manual deploy needs `npm i -g firebase-tools && firebase login`, then `npm run build && firebase deploy`.

`firebase.json` rewrites all paths to `/index.html` for client-side routing, and caches `assets/**` for a year while serving everything else `no-cache`. Vite's content-hashed filenames are what make that safe.

## Architecture

**Routing is the hub, and it spans two files.** `src/pageDefs.ts` holds the bare `PAGES` list (`path` + `routeName`, `as const`); `src/routes.tsx` builds `ROUTES` from it by attaching an element and a `nodeRef`. Between them they are the single source of truth for four things:

1. the router config (`ROUTER`, via `createBrowserRouter`),
2. the nav links rendered by `src/App/NavBar.tsx`, which maps over `ROUTES`,
3. a per-route `nodeRef` that `ContentPortal` needs for page transitions,
4. `sitemap.xml`, generated by the `sitemap` plugin in `vite.config.ts`.

**To add a page**: add an entry to `PAGES`, add a `lazy()` import in `routes.tsx`, and add its element to `ELEMENTS`. The nav and the sitemap update themselves. `ELEMENTS` is typed `Record<PagePath, ReactNode>`, and `PagePath` is derived from `PAGES` via `as const`, so skipping step three is a compile error rather than a runtime blank page — don't loosen that type. The `nodeRef` is attached by the `.map()`, so never hand-write it.

`pageDefs.ts` must stay free of JSX and React imports: `vite.config.ts` imports it directly, and it is named `pageDefs` rather than `pages` to avoid colliding with the `src/pages/` directory. `NOT_FOUND_NODE_REF` is exported separately because `NotFound` is deliberately absent from `PAGES` (it belongs in neither the nav nor the sitemap).

**Render tree.** `src/index.tsx` mounts `StrictMode > ErrorBoundary > Suspense > RouterProvider`. All pages are `lazy()`-loaded, so the single `Suspense` at the root is what catches every route's loading state.

**Page transitions.** `src/App/ContentPortal.tsx` wraps the outlet in `SwitchTransition` + `CSSTransition`, keyed on `location.key` with a 250ms `fade`. React Transition Group needs an explicit `nodeRef` under StrictMode, which is why the refs live on the route definitions rather than being created locally. The duration exists twice — `TRANSITION_MS` in the `.tsx` and `$transition-time` in the `.scss` — and the two must be changed together.

## Conventions

- **Components are directories**: `ComponentName/index.tsx` + `ComponentName/index.scss`, default-exporting the component. `src/components/index.ts` re-exports them as named exports, so import from `'../../components'`, not the individual paths.
- **`import/no-default-export` is an eslint error** for plain `.ts`/`.js` files, and turned off for `*.tsx`, `*.jsx`, `*.d.ts`, and `*.config.*`. That is the reason for the default-export-plus-barrel pattern above.
- **Shared prop type**: `ComponentProps` (`className?`, `children`) in `src/components/types.ts`. Components that take a `className` compose it with `clsx('BaseClass', className)`; the SCSS then styles modifiers as `&.small`, `&.subtitle`, etc.
- **SCSS**: `src/_common.scss` holds the colors, fonts, `link` mixin, and a `respond-to` mixin with `phone`/`tablet`/`desktop` breakpoints. No sass `loadPaths` are configured, so it is imported by relative depth — `@use "../common"`, `@use "../../common"` — and referenced namespaced (`common.$bg-color`).
- **Class names match component names** (`.NavBar`, `.Header`, `.Project`). There is no CSS-modules or scoping layer, so keep them unique.

## Gotchas

- **`no-script.css` must stay outside the app's CSS pipeline.** In dev, Vite injects imported CSS via JS, so `index.scss` never loads with JS disabled; only `vite build` extracts it to a static `<link>`. The `<noscript>` block in `index.html` therefore links `/no-script.css` directly. It is _generated_ from `src/no-script.scss` by the `no-script-css` plugin in `vite.config.ts` — emitted at build, compiled per request in dev — which is what lets it share `src/_common.scss` instead of hardcoding the palette. Never import `src/no-script.scss` from application code, and don't reintroduce a static copy in `public/`. There is a comment in `index.html` explaining this — leave it.
- **`vite.config.ts` has a dev-only middleware** redirecting `/.well-known` to `/`. In production Firebase serves `public/.well-known/xrp-ledger.toml` directly with its own CORS and content-type headers.
- **`sitemap.xml` is generated, not committed.** The `sitemap` plugin in `vite.config.ts` emits it during `generateBundle` and serves it from memory in dev, both from `PAGES`. Don't add a static copy to `public/` — it would be a second source of truth. The absolute URLs come from `SITE_ORIGIN` in `vite.config.ts`, which is the one place the production domain is hardcoded.
- **Dependencies are pinned below the current majors on purpose.** TypeScript is held at 6.x and ESLint at 9.x; both majors are blocked by ecosystem lag (TS 7 ships no JS compiler API and `typescript-eslint` rejects it; ESLint 10 breaks `eslint-plugin-react` and `eslint-plugin-import`, which use APIs removed in v10). Everything else is already at latest. Verify before assuming an upgrade is available.
